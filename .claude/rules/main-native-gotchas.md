# Native Electron traps (main process)

These traps only concern the main process's native code (WebContentsView,
windows, global shortcuts, macOS Spaces). They load when you edit
`src/main/**`.

1. **`WebContentsView` is NOT a DOM element.** It is a native layer placed on top of the window at explicit x/y/w/h coordinates. When the chrome moves (resize, a sidebar opening), you have to **recompute and reposition the view by hand**. It is the classic Electron browser bug.
2. **Do not use `<webview>` or `BrowserView`** — deprecated. Always `WebContentsView`. (AI often suggests the old `<webview>`: correct it.)
3. **An HTML overlay on top of the web content is impossible; it takes a native window.** Corollary of #1: since the `WebContentsView` is composited **above the whole chrome DOM**, a CSS/absolute bubble (tooltip, popover, context menu) that overflows onto a tab's area is **hidden behind the page**. The native `title=""` tooltip is NOT a fallback option: it is **broken on Electron 41.x macOS arm64** ([#49843](https://github.com/electron/electron/issues/49843), fine in 37.x), on top of being unstylable and delayed. The only way to draw above web content is a **native window** that the OS composites higher: a transparent child `BrowserWindow` + `focusable:false` + `setIgnoreMouseEvents(true)`, shown with `showInactive()` (a sibling `WebContentsView` layer restacked on top also works, but its alpha above a sibling view is reputed unreliable). Implemented for the status bar tooltip: `show-tooltip`/`hide-tooltip` commands (registry), pure tested geometry in `src/main/tooltip.ts`, native overlay in `src/main/profiles.ts`.
4. **`globalShortcut` registers by QWERTY key position, not by character.** On a French AZERTY keyboard, the accelerator `'M'` lands on keycode 46 (QWERTY M position = the "," key on AZERTY): the physical M key (keycode 41, QWERTY ";" position) triggers nothing. Verified for real (simulated keystroke by keycode vs real keystroke). Workaround: register both accelerators (`'M'` and `';'`) on the same handler — see the focus-app shortcut in `src/main/index.ts`. Affects every letter that moves between QWERTY and AZERTY: A, Z, Q, W, M.
5. **macOS virtual desktops (Spaces) are invisible to Electron.** All Spaces share the same coordinate plane (same x/y on desktop 1 and desktop 3), and a relaunched app ALWAYS opens its windows on the current desktop: saving/restoring the bounds never restores the desktop. No public API (neither Electron nor AppKit) places a window on a given Space — the only way is the private SkyLight API, and `SLSMoveWindowsToManagedSpace` **only works for the calling process's windows** (locked for other apps' windows since macOS 14.5 — verified for real on Darwin 25: move refused on a Calculator window, accepted on one of our own windows). Hence the `native/mira-spaces/` addon (thin wrappers), the pure logic in `src/main/spaces.ts` (indexing by Mission Control order — Space ids change at reboot, the index does not), the `spaceIndex` field of `session-store.ts`, and the `list-spaces` / `move-window-to-space` commands. Another trap in there: moving a window to another desktop through Mission Control emits NO Electron event (same coordinates) — the capture happens on `focus` and at close.
6. **`chrome.runtime` already has two owners before you, one per world.** On the **extension service worker** side, the `electron-chrome-extensions` preload rebuilds `chrome.runtime` from scratch (`{...base, …}`) then does `Object.freeze(chrome)`: a shim registered BEFORE the lib is thrown away with the original object. The freeze only covers `chrome` itself, so the workaround is to register your preload **after** `new ElectronChromeExtensions(...)` and to assign on `chrome.runtime`, which stays extensible. On the **web page** side, `stealth.ts` installs a DECOY `chrome.runtime` on every page (`sendMessage` no-op, so that `window.chrome` does not smell headless): a page API that looks present but whose callback never fires comes from there, not from the site. `stealth.ts` guards itself with `if (!c.runtime)`, so a shim that overwrites its methods and keeps its enums survives its re-assertions on `did-navigate`/`dom-ready`. Both traps were paid for while implementing `externally_connectable` (see the headers of `src/main/external-messaging*.ts`).
7. **No web push notifications: Electron provides no push service, and no flag changes that.** `ElectronBrowserContext::GetPushMessagingService()` returns `nullptr` (`shell/browser/electron_browser_context.cc`, verified on tag `v41.7.0` = the version we ship), so every `registration.pushManager.subscribe()` fails with `AbortError: Registration failed - push service not available` (verified for real on drive.google.com). **Do not confuse it with a permission problem**: `permissions.ts` grants everything, `Notification.permission` is `granted` and the site's service worker installs normally — it breaks one step further, at subscription. The shipped binary contains no trace of the GCM/FCM stack (neither `gcm_driver` nor `mtalk.google.com`), so there is nothing to enable on the command line; the upstream ticket [electron#6697](https://github.com/electron/electron/issues/6697) has been open since 2016. Symptom on the site side: Google Drive shows "Impossible d'activer les notifications" (its French UI string for "Unable to enable notifications"). Libraries like `electron-push-receiver` only serve an app that has its own FCM back end, never to make a third-party site's notifications work.
8. **Working around the lack of push (if it is ever worth it): the deciding point is `ServiceWorker.deliverPushMessage`.** The only way without recompiling Chromium comes in four pieces: shim `PushManager.prototype.subscribe` on the page side to return a subscription whose endpoint points to us (P-256 keys generated locally), a public relay that takes the web push POSTs (RFC 8030), RFC 8291 decryption on the main side, then delivery to the site's service worker through the CDP command `ServiceWorker.deliverPushMessage(origin, registrationId, data)`. Two unknowns were cleared by driving a Drive page: the site asks for a **standard VAPID key** (65 bytes, `0x04` prefix, so standardised web push, not a proprietary Google channel), and the server **accepts an endpoint on an arbitrary domain** (RPC `gDYDgb` of AppsNotifyUi, 200 response, endpoint returned as is) — so nothing on the site side blocks the setup. The unknown that decides everything remains, **unverified**: the CDP `ServiceWorker` domain is **browser-level**, not page-level, and we do not know whether it is reachable from `webContents.debugger` (Electron exposes no browser target; it would probably have to go through `--remote-debugging-port`). Test this first before writing anything else.
9. **`chrome.storage.onChanged` never arrives in an extension service worker.** Electron only dispatches storage changes to **renderers**: an extension page receives everything (including the writes made by the SW), the SW receives nothing — not even its own. Reading and writing, on the other hand, works and is properly shared: the SW rereads what the page wrote. Measured with a probe extension (`permissions: ["storage"]`, a SW listening to `chrome.storage.onChanged`, `local.onChanged` and `session.onChanged`). It is a **silent** hole of the worst kind: `addListener` does not throw, feature detection passes, and the extension waits for an event that will never come. What it cost: Bitwarden unlocked in the popup, but its SW believing itself locked forever (its cross-context `updates$` is built on `<area>.onChanged`), hence "Unlock your vault" in every page's context menu. Filled by `src/main/extension-storage-events*.ts` — each context reports its writes to main, which pushes the change set into the SW, where a shimmed `onChanged` distributes it. **The shim is installed with `Object.defineProperty`, never by assignment**: an _area_'s `onChanged` is an accessor without a setter (`chrome.storage.session.onChanged` → `get: true`), so `x.onChanged = …` is silently ignored in sloppy mode and the inert native event survives — that is what made the bridge's first draft completely ineffective, without the slightest error. The top-level `chrome.storage.onChanged`, by contrast, is a data property. **And the bridge carries no value across**: it reports key names, the worker builds `{newValue: undefined}` for a save and `{}` for a removal (`'newValue' in change` stays accurate, `oldValue` is not provided). Measured reason: Bitwarden keeps its decrypted vault in a single `chrome.storage.local` key of over a megabyte that it rewrites at every sync — carrying the values put a few MB of IPC per write on its worker's hot path, which never rebuilt its menu again. Same ordering constraint as trap #6: the preload must register **after** the lib, whose freeze of `chrome` is shallow (`chrome.storage` stays extensible, `set` stays writable).
10. **A child window shown with `showInactive()` raises its PARENT window in front of the other apps.** Nasty corollary of #3: the native overlay (toast, tooltip, bubble) is a child `BrowserWindow`, and ordering it in front raises the parent with it — so an overlay flashed while Mira is behind the terminal brings the whole browser window in front of what the user is doing, and it stays there after the overlay disappears. `focusable:false` and `showInactive` do not protect: they prevent stealing **keyboard focus** (the frontmost app does not change), not the rise in the **z-order**. Reproduced by firing `show-toast` alone, Mira behind a terminal: the Mira window moved in front of the terminal in 0.3 s and stayed there. Original symptom: "a finished download brings Mira to the front" — it was the completion toast, not the download. Workaround in place: `mayShowToast` (`src/main/toast.ts`) only allows a toast if its window has OS focus; in the background, the status bar's "unseen" badge carries the information. Take the same precaution for any new native overlay triggered by an asynchronous event (end of a task, capture, sync).
11. **`showInactive()` on a top-level window places it ABOVE all apps.** Same mechanism as #10, without a child this time: the app stays inactive and the keyboard does not move, but the window lands at the top of the z-order. Reproduced: an `open-profile` through the socket placed the test profile's window above the terminal, the terminal remaining the active app. That is what bothered parallel Claude sessions (one window per session, covering what the user is reading). Electron has no "show below"; AppKit does: `-[NSWindow orderWindow:NSWindowBelow relativeTo:<number>]`, which accepts a window of ANOTHER app as reference and does not activate the calling app (verified with a throwaway Swift binary in `activationPolicy = .prohibited`; in `.accessory` the binary activated itself at launch and the test was wrong). Workaround in place: `showBehind` in `profiles.ts` (window created with `inactive`), `native/mira-spaces` addon (`onScreenWindows`, `orderWindowBelow`), choice of the reference window pure and tested in `src/main/window-order.ts`. A covered window stays drivable: the same day, page text modified while another window covered it, `screenshot` rendered the modified text, `requestAnimationFrame` fired, and the page even reported itself `visible`.
12. **A window entirely covered by another one no longer takes input: Chromium declares it "occluded", hides its web contents, and the renderer stops painting.** `backgroundThrottling: false` on the tab (`materializeTab`) is not enough under Electron 44.4.1, contrary to what an earlier measurement (Electron 41) suggested. Measured with a probe page (capture-phase listeners for `pointerdown`, `mousedown`, `keydown` on `window`): in the build of the day (`fb0fae4`) then in a dev instance, `click`, `press-key` and `type-text` answered ok while the page received no event, `visibilityState` was `hidden` and a `requestAnimationFrame` did not fire in 2.5 s. It affects the session window (born covered by `showBehind`) as well as an ordinary profile window as soon as it is entirely covered; a window visible on screen does not have the problem. **Cause established by A/B** on the dev instance, same window, same page: without the Chromium switch `disable-backgrounding-occluded-windows`, input lost; with it, click and keystroke received (`isTrusted: true`), page `visible`, frames painted — two passes by hand then one with the switch in the code. **Workarounds in place**: (a) the switch, in `src/main/chromium-switches.ts`, applied before `app ready`; (b) delivery verified AFTER the dispatch, on proof (`src/main/input-delivery.ts`, `dispatchChecked` in `profiles.ts`): lost input makes the command fail (`input was dropped`) instead of answering ok. Cost of the switch not measured: a covered window keeps painting. **To replay the measurement without touching the running Mira**: `MIRA_SOCKET=/tmp/mira-dev-probe.sock npx electron-vite dev -- --user-data-dir=<throwaway folder>` — without `MIRA_SOCKET`, the dev instance deletes and takes over `/tmp/mira.sock` (`socket.ts`, `listen`), and without `--user-data-dir` it shares the real userData.
13. **A `BrowserWindow`'s `ready-to-show` fires again on every page load of ANY tab.** Electron 44 relays the event from every `webContents` the window owns, tab `WebContentsView`s included (`lib/browser/api/web-contents.ts`, `owner.emit('ready-to-show')`, read on tag `v44.4.1`). A handler registered with `on` that does `window.show()` therefore replays an `activateIgnoringOtherApps` on every navigation and brings Mira back in front of the user. Found in `activation.log`: all of a day's out-of-focus activations came from that `window.show()`. Workaround: `once('ready-to-show', …)` in `profiles.ts`. Every handler on `ready-to-show` must be `once`.
